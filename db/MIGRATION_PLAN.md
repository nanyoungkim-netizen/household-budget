# 데이터 저장 구조 개선 계획 (통짜 JSON → 항목별 테이블)

## 왜 하나
지금은 **모든 데이터를 `user_data` 테이블의 한 행(JSON 통짜)** 에 저장한다.
이 때문에 두 가지 문제가 생긴다.

1. **저장이 무겁고 자주 실패** — 한 글자만 바꿔도 전체를 다시 올린다. 데이터가
   커지면 느려지고, 클라우드가 잠들었다 깨는 시간과 겹치면 "저장 중…"이 돌다 실패.
2. **여러 기기에서 데이터 유실** — 다시 접속하면 "클라우드 = 최신"이라 가정하고
   기기 내용을 통째로 덮어쓴다. 마지막 저장이 실패한 상태였다면, **방금 한 작업이
   옛날 클라우드 내용으로 덮어써져 사라진다.** (실제로 "내역만 날아가고 예산은 남음"
   현상의 원인)

## 목표 구조
데이터 종류별 테이블 + **한 건씩 행(row)** 으로 저장.
- 거래 1건 추가 = 행 1개만 저장 → 가볍고 거의 안 실패
- 폰에서 넣은 거래 / 컴퓨터에서 넣은 거래 = 서로 다른 행 → **둘 다 보존**
- 삭제는 진짜로 지우지 않고 **`deleted_at` 표시** → 다른 기기에서 되살아나는 사고 방지
- 같은 항목이 양쪽에서 바뀌면 → **`updated_at`(최신)** 기준으로 정리

## 테이블 (총 22개) — `0001_per_entity_tables.sql`
가계부 목록(`ledgers`), 가계부별 설정(`ledger_settings`), 계좌, 카테고리, 거래내역,
예산, 카드, 할부, 적금·예금, 적금납입, 목표, 목표납입, 카드청구, 매핑규칙,
투자계좌유형, 투자계좌, 보유종목, 투자거래, 배당금, 예수금, 포트폴리오, 관심종목.

공통 컬럼: `id`(앱 식별자), `user_id`(소유자/보안기준), `ledger_id`(어느 가계부),
`updated_at`, `deleted_at`. 모든 테이블에 **RLS(내 행만 접근)** 적용.
> ※ '환급'은 거래의 한 유형(`type='refund'`)이라 **거래내역 테이블에 함께** 들어간다.

## ✅ 기존 데이터 안전 보장
- 이 작업은 **새 테이블을 추가만** 한다. 기존 `user_data` / `user_data_versions`,
  각 기기 localStorage는 **그대로 둔다(원본 보존)**.
- 이사 = 기존 JSON을 **읽어서 새 테이블에 복사** (원본을 지우지 않음).
- 시작 전 **엑셀 백업** 권장. 새 구조가 검증될 때까지 **기존 시스템 유지**.
- 즉 "복사 → 건수 확인 → 그다음 전환"이라 원본이 사라질 일이 없음.
